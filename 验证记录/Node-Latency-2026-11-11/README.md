## 本次修复

Android `NodeRouteInterceptor` 在收到 IOException 时，先清空路由验证时间，再判断请求是否取消。切换页面、替换订阅等主动取消会因此让健康路由失效，下一次读取必须重新探测，并发请求还会等待路由选择锁。

改为先判断取消：取消只终止当前请求，保留既有路由验证时间；原有 15 秒有效期、真实 I/O 故障重新探测、502/503/504 自动切换和禁止重放写操作均保留。未扩大缓存有效期或减少身份校验。

## 约 1.4 MB 响应的确定根因与修复

通过本机临时配对诊断连接读取真实 JSON 响应，只输出字段名称、大小、编码和耗时，不保存原始响应或图片。每次诊断在 finally 中撤销连接。只读检查 queued_tasks 确认一条 failed 队列任务的 input 含 data:image 内嵌图片，图片 URL 字符串约 1,885,831 字节。

具体传播路径：

1. `ExecutionQueue._public()` 保留恢复任务的完整 input，这是所属会话恢复所需的原始数据。
2. `execution_projection()` 把完整恢复任务放进 `recoveryTask`。
3. `ActivityRegistry.observe_execution()` 将该投影存入节点级活动表，旧版 `snapshot()` 原样深复制全部字段，导致单行任务约 1,886,639 字节。
4. `/v1/activity` 返回全局活动；`CodexService.get_session()` 又在每个会话响应中附带同一份全局 activity。故打开与失败任务无关的会话，也会携带同一张图片。
5. Android 活动同步和会话同步均有 5 秒回退读取，并受生命周期事件唤醒；同一个正文在独立活动请求和会话请求中反复下载。两回合历史确认只能省去历史部分，不能省去 activity；压缩已生效，但图片数据压缩后仍约 1.39 MB。

本地修复：全局活动 snapshot 不再包含 `recoveryTask` 正文，保留 recoveryRequired、deliveryState、blockReason、threadId 等状态及定位字段。App 活动行只解析 ThreadSummary，不消费恢复任务正文。内部队列、图片原件、所属会话的完整 recoveryTask 与恢复操作不变。未通过删除失败任务掩盖问题。

使用新实现的 ActivityRegistry.snapshot 对真实响应作内存回放，保留其余全部字段，按线上 JSON 和 gzip level=1 序列化：

| 响应 | 原 gzip 字节 | 修复后 gzip 字节 |
| --- | ---: | ---: |
| 活动状态 | 1,394,839 | 5,209 |
| 普通会话样本 0 | 1,403,116 | 13,528 |
| 普通会话样本 1 | 1,407,172 | 17,493 |

这是相同真实数据的离线体积对比，不是已部署后的手机耗时测量。直接打开失败任务所属会话仍可能返回较大的恢复输入，属于后续可单独优化的按需附件读取范围。

新增回归以约 1.9 MB 内嵌图片构造恢复任务：旧版全局 snapshot 大于 1.9 MB，测试失败；新版摘要小于 2 KB，保留恢复标记及所属会话完整输入，测试通过。`test_activity`、`test_activity_read_scope`、`test_client_projection` 共 66 项通过，`git diff --check` 通过。未部署，未真机或模拟器验证，不将体积降低等同于端到端等比例提速。
