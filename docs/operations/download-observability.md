# 公网下载诊断

2026-11-10 已部署到当前 VPS。前端为 HAProxy 8443，后端为 127.0.0.1:18080。

当前客户端方案已简化为单连接下载，见文末。下方分段实验和 0.2.97 测试包记录为历史证据，不代表当前代码。

## 数据来源与语义

- `scripts/haproxy-download-observability.cfg` 是 `frontend rivo_public` 内的配置片段。只记录更新包路径的请求，不记录 URL、查询串、令牌、Cookie 或正文；其他请求静默。
- 完成日志 `rivo_public_download` 包括 peer/local、状态、字节数、后端连接与响应头耗时、active_ms、termination、后端生成的 download_id 和 Range 标记。`fc_*` 来自前端公网 socket，不再误用后端 loopback 指标。
- `retrans_inflight`、`lost_inflight` 是当时在途计数，不是累计重传。HAProxy 的 active_ms 结束于数据交给内核，可能早于客户端收到全部内容，不能单独当作实际下载耗时。
- `scripts/sample-download-tcp.py` 每秒只采样 8443 established socket，记录 connection-wide 累计收发/重传、RTT、cwnd、snd_wnd、发送队列及 rwnd_limited/sndbuf_limited 时长。按 peer/local 和时间与请求日志关联；同连接多次请求不能直接把累计计数当作单请求计数。
- 短于采样周期的连接可能没有快照；closed 的 last_* 只是最后一次采样值，不是关闭瞬间最终值。缺失指标不推断为零。

## 部署与维护

脚本安装为 `/opt/rivo-relay/diagnostics/sample-download-tcp.py`，unit 使用 `scripts/rivo-download-tcp.service`，运行用户 rivo-gateway。日志在 `/var/log/rivo-download/tcp.jsonl`，目录 0700、文件 0600；每文件 2 MiB，保留 3 份备份，最多约 8 MiB。只含网络元数据，无应用内容。服务 MemoryMax=64M，最多采样 512 条连接，ss 命令最多等待 3 秒。

修改 HAProxy 前备份并执行 `haproxy -c -f /etc/haproxy/haproxy.cfg`，通过后 reload。当前备份为 `/etc/haproxy/haproxy.cfg.before-download-logging`。不重启 Codex 原生运行时、不修改更新清单。停止采样用 `systemctl disable --now rivo-download-tcp`；回退代理日志仅恢复备份并检查配置后 reload，不删除证书及密钥。

读取：

```sh
journalctl -u haproxy --since '10 minutes ago' --no-pager | grep rivo_public_download
tail -n 60 /var/log/rivo-download/tcp.jsonl
```

## 实测与优化依据

- 受控 128 KiB/s 接收实验：发送窗口降至 64 字节，rwnd_limited 占忙碌时间约 96%，证明能识别接收端限速。此项不能用来证明用户手机也受接收窗口限制。
- 不限速单连接复现：19,508,787 字节耗时 14.344 秒，前 14 秒约 65–260 KiB/s；到采样末期累计重传 408 段，cwnd 最低 4，发送队列约 1 MiB。接收窗口约 155 KiB，后端响应头仅 1 ms。下一条单连接耗时 0.693 秒，证明存在连接间波动，不能凭一次快测宣称已解决。
- 3 并发、512 KiB 分段、每段独立连接的两轮对照用时 1.159/1.343 秒，最终 SHA-256 一致。基于此实现客户端有界分段下载，仅用于本部署的大更新包，服务器不支持 Range 时回退旧下载器。
- 客户端每段最多 3 次尝试、最多 3 个 worker、每段缓存最多 512 KiB；乱序写入固定范围，最终流式 SHA-256 验证通过才能生成 APK。取消会关闭所有在途请求并清理临时文件。
- 开发机实测不能代替新版手机验收；旧版手机的公网路径已捕获，见下方复现记录。当前不进一步修改 BBR、队列、MTU 或系统窗口参数。

原始证据在独立工作目录 `workspace/artifacts/download-observability/`，含源 IP，仅本地保留，不纳入 Git。

## 用户手机复现（12:55，北京时间）

用户回复“已开始”后捕获实际下载。首请求 trace `524e4520262c48bc9f7775f24326cc2b` 约 4.4 秒后由客户端断开（CD）；续传 trace `67390ee7d461455e9bc8d7be80eb05bc` 返回 206，代理 active_ms 为 31,797 ms，TCP 忙碌时间约 33.6 秒。

续传前两秒 ACK 增量约 138 KB、99 KB，RTT 约 174–205 ms。结束采样累计重传 1,172 段、1,547,040 字节；rwnd_limited 仅 295 ms（不足 1% 忙碌时间），服务端长期有待发送数据。后端连接 4 ms、响应头 1 ms。这次实测主瓶颈是公网传输重传与拥塞窗口恢复，不是文件读取、手机接收窗口长期关闭或纯 UI 速度显示。仅凭 VPS 无法定位具体丢包设备，也不能仅凭出口 IP 判断 VPN 状态。

中途曾升到约 1 MB/s 后再次下降到约 170–400 KB/s，末期约 1.5–1.7 MB/s，不是单纯一次正常慢启动。此记录来自旧单连接下载器；分段方案还未进行手机端对照验证。

## 新版手机回测（13:41，北京时间）

用户确认安装新版并重新下载后：13:40:51 的首轮分段请求中有客户端断开，不能作为完整耗时比较；13:41:14 至 13:41:57 出现完整一轮 HEAD + 38 个独立 Range 请求。38 个分段均为 206、代理正常结束，37 个 512 KiB 段及尾段与测试包大小相符；没有观察到该轮 HTTP 错误或额外重试请求。服务器日志不能代替客户端最终文件摘要验证。

从 HEAD 完成到最后一段代理完成约 43 秒，对应约 454 KB/s（约 443 KiB/s），只是服务端时间窗口估算，不是手机端精确完成耗时。仍明显低于用户预期 3.4 MB/s，不能宣称优化成功。分段 active_ms 中位数 1,013 ms、最大 1,866 ms，后端响应头最大 2 ms；公网 RTT 中位数约 186 ms。

采样仍有重传证据；但每秒只采样 established socket，短连接关闭后尾部数据不可见，因此该轮累计计数不完整，不能与旧长连接的 1,172 次重传直接比较。例：首个连接采样 cwnd 从 10 增到 79 后结束，后续新连接重新从较小窗口起步。当前 512 KiB 每段 Connection: close 强制新建连接，在该高 RTT 手机路径上反复支付握手和拥塞窗口增长成本，是下一步需对照验证的实现开销。建议比较有界并发下复用健康连接、仅替换持续低速连接与适度增大分段；尚未修改或验证此方案，不将全部等待归因于握手。


## 最终简化方案

按用户要求，删除并发分段下载器及其专用测试，不再每 512 KiB 重建连接；同时删除旧更新器中“3 秒低于 256 KiB/s 就主动断线”的判断。

- 设置页继续使用原有单连接流式下载，只有实际传输异常才有限重试（最多 3 次尝试），根据已接收字节使用 Range 续传，并验证声明长度和 SHA-256。
- 聊天更新包链接直接复用现有 ResumableDownload，只在下载完成后增加路径摘要校验；删除 HEAD 探测和分段回退分支，不再维护额外下载算法。其他普通文件的下载方式不变。
- 保留 VPS 的有界诊断日志，不调整网络参数。不以本次代码简化宣称公网链路已恢复预期速度。
- 本次未构建或上传新 APK；先前 0.2.97 / 109 仍是分段实验包，不能拿它验收简化后的实现。后续交付包必须使用更高 versionCode，不覆盖已提供的测试包。

简化后验证：17 项相关单元测试通过（更新下载 8 项、公共链接 2 项、通用续传 7 项），必要 Kotlin 编译通过，git diff --check 通过。包含约 160 KiB/s 慢连接保持单次 GET、断线续传、取消、范围校验和摘要错误拒绝。未运行 lint，未进行新版真机或模拟器验收。
