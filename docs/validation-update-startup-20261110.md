# 更新起步低速排查（2026-11-10）

## 证据与边界

- 现网最新包为 0.2.90，19,476,015 字节。源码修复基于 origin/main ad13e69 的独立工作目录，未包含另一工作区正在进行的会话置顶改动。
- HAProxy 上线后，程序设置的 BBR 仅作用于 127.0.0.1 后端连接；公网 HAProxy 80/8443 连接原本为 CUBIC。应用日志的 TCP 指标不是手机连接指标。
- 将 VPS TCP 默认算法改为 BBR 并 reload HAProxy 后，ss 确认新公网连接使用 BBR；已有连接维持原算法。此系统设置影响 VPS 后续新 TCP 连接，不仅 Rivo。
- BBR 单独不能解决全部问题。80 端口复现整包 21.38、28.349 秒，第一 MiB 约 8.2 秒，前段约 65–475 KB/s，尾段突增；一次公网连接发出约 480 KB 中约 209 KB 为重传。首字节约 40–400 ms，主要耗时在传输中。
- 同轮 8443 整包 0.398、0.532 秒，另两次为 1.755、1.475 秒；所有完整下载 SHA-256 一致。开发机存在链路波动，不能把这些结果当作手机速度保证，也不能仅凭此认定运营商的具体限速策略。
- 临时 FQ 调度实验未消除 80 起步低速，已恢复原 mq + fq_codel；没有持久化未经证实的 FQ 调参。

## 修复

- App 内更新对本部署的 134.175.156.219:80/8443 路由统一使用 https://134.175.156.219:8443，清单与 APK 都走该入口，校验系统 CA 与 IP 身份，无配对令牌、无重定向。
- 活动节点与旧保存更新源均覆盖。其他部署保留既有 pin；节点会话连接与配对信息保持原样。
- VPS `/etc/sysctl.d/90-rivo-proxy-bbr.conf` 持久化 `net.ipv4.tcp_congestion_control = bbr`。撤销时删除此文件并恢复原 cubic，再 reload HAProxy；已有连接不会因此改变。
- 需要安装修复包后，App 内“检查更新”才使用新入口。旧版可直接打开 8443 下载链接。

## 验证

逐秒字节数、首字节、1 MiB/4 MiB 时间和 SHA-256 证据留在原工作区 `workspace/artifacts/proxy-download-20261110/`。最终修复包为 0.2.92（104），仅用于验收，不修改正式 latest 清单；真机体验待用户确认。

最初仅迁移入口的候选包验证后，8443 也复现 33.138 秒完整下载（首段约 0.101 秒），因此不能将更换端口当作充分修复。随后增加首次低速连接恢复：传输超过 3 秒，平均低于 256 KiB/s 且剩余大于 1 MiB 时，主动取消该连接并 Range 续传一次；后续连接不再按低速主动重试，保留原有最多 3 次传输错误重试上限。该处理不伪造速度、不重新从头下载，最终仍检查整包哈希。VPS 上传前更新目录约 137 MB，磁盘可用约 37.9 GB。

最终验证：8 项 NodeAppUpdatesTest 全部通过（包含持续低速但不掉线、主动取消旧连接后 Range 续传、整包哈希一致），assembleDebug 成功；0.2.92（104）签名与当前发布包一致，SHA-256 `794cf6bd083d3453357c456214c139df3f6f4218d74a28e0faccc9e087350f00`。测试包只提供手动下载，正式更新清单保持不变。原始手机网络丢包位置尚无法仅凭 VPS 定位；恢复机制与入口变更需手机复测，不承诺每条链路固定速度。
