# App 与节点兼容协议

状态：已实现于本分支，尚未发布。本文规定兼容声明、能力门控与更新判断；上线前仍需单独发布。当前接口形态见 [HTTP API](API.md)，更新部署见 [VPS 统一更新](central-updates.md)。

## 目标与边界

采用“稳定的 API 主版本 + 可选功能声明”。App 与节点独立发布，软件发布版本（versionName、versionCode、releaseCode）只用于更新排序、展示和诊断，不用于推断通信兼容性。不维护两份客户端/服务端发布版本兼容列表。

兼容性由双方实际实现的 API 主版本决定：存在共同版本，就使用双方都支持的最高主版本；没有交集则基础通信不兼容。声明支持某个版本意味着实现其完整基础契约，不能只返回版本号。新版 App 可以连接旧节点，旧 App 也可以连接新节点，但双方必须仍实现共同的契约。

本协议描述 App 与 Relay 节点之间的 HTTP/SSE 契约，不等同于节点与 Codex 原生运行时、VPS 分发协议、数据库或 bootstrap 的版本。API 兼容也不表示节点在线、登录有效、原生运行时可用或当前会话允许写入。

## API v1 基础契约

`/v1` 是长期维护的契约，不随每次软件发布递增。以下是基础通信与文本聊天的必需范围；字段结构、请求限制及状态含义沿用 [HTTP API](API.md) 的对应章节。该文档的其他功能不因处于 `/v1` 路径就自动成为基础能力。

| 范围 | 必需接口或行为 |
| --- | --- |
| 身份与连接 | `POST /v1/pair`、`GET /v1/node`；保留节点 ID、Bearer 鉴权及令牌撤销语义。`GET /health` 仅供健康诊断，不能代替兼容或原生就绪判断。 |
| 项目与会话读取 | `GET /v1/projects`、`GET /v1/threads`、`GET /v1/threads/{id}`、`GET /v1/threads/{id}/history`；保留稳定身份、历史分页及只读状态语义。 |
| 基础文本交互 | `POST /v1/threads`、`POST /v1/threads/{id}/turns`、`POST /v1/threads/{id}/interrupt`、`POST /v1/requests/respond`；保留创建、发送文本、中断和原生审批响应的请求与回执语义。基础发送不能依赖某项可选功能。 |
| 提交结果 | `GET /v1/submissions/{submissionId}`；写操作遵守稳定 submissionId、去重和 pending/unknown/accepted/failed 状态语义；HTTP 200 不等于操作成功，断网、超时、503 或回执 404 不等于未执行。结果未知时只核对，不换 ID 自动重发。 |
| 事件与恢复 | `GET /v1/events` 的 SSE、Last-Event-ID、重置、撤销及重连语义；按稳定身份合并重复事件，缺口/重置后重读快照，不重复执行写操作。 |
| 错误与权限 | 保留 HTTP 状态及 `error.code` 的含义，不以错误文案判断行为；未知状态不能推断成功或写入权限，最终操作仍由服务端检查。 |

基础契约要求接口和语义存在，不保证每次业务请求成功；会话只读、运行时不可用、审批过期等仍按既有错误和状态处理。语音、目标模式、附件、待办及其他扩展按能力启用，缺失不应阻断基础文本聊天。

### 同一主版本内的演进规则

- 服务端可新增接口及可选字段，但不能删除或改名既有基础接口/字段、改变字段类型与含义，或把新的请求字段变成必填。省略新增参数必须保留原行为。
- 客户端忽略不认识的附加字段；只有契约明确允许缺省的字段才使用约定默认值。不能用宽松解析掩盖必需字段缺失或非法数据。
- 新响应枚举、历史条目类型及 SSE 通知必须有安全的未知值处理：可以展示未知活动或重新读取快照，不能推断已完成、允许写入或自动回答审批。若旧客户端无法安全处理，该变化就不能作为同一主版本的普通增量。
- 新客户端保留基础调用路径；调用可选功能前检查能力，不把新增参数或接口无条件加入基础流程。
- 不兼容的基础变化引入 `/v2` 等新主版本，过渡期间显式保留 v1 实现。增加版本声明不能替代实际的适配实现；不要求永久支持所有历史主版本，但移除支持前必须经过更新兼容判断并说明迁移影响。

## 兼容与能力声明

在现有鉴权接口 `GET /v1/node` 中新增可选的 `compatibility` 对象，作为稳定的发现入口。即使未来业务仅支持 v2，也保留此发现入口及既有身份/鉴权语义；发现入口位于 `/v1` 不代表该节点仍支持 v1 业务。

节点声明结构如下（实际能力清单见下表）：

```json
{
  "compatibility": {
    "apiVersions": [1],
    "features": {
      "1": ["voice.direct", "session.goals"]
    }
  }
}
```

- `apiVersions` 是非空、无重复的正整数集合，准确列出节点完整实现的基础 API 主版本。App 内也声明自己实际支持的集合。
- `features` 按主版本列出可选能力字符串集合；缺少某版本的条目或某个能力表示该版本下不支持此能力。未知能力名忽略，不能通过软件版本号猜测支持。
- 两端根据共同版本选定实际请求路径；当前只有 v1 时没有额外握手。App 只调用自己认识且在所选版本下被节点声明支持的能力。
- 现有 `capabilities.media/speech` 等结构化字段保持原状，不改为字符串数组。`compatibility.features` 表示接口契约已实现；现有能力接口、运行时状态及会话状态继续决定此刻能否使用。声明支持语音不代表语音后端此刻在线。
- 每个能力须在功能文档登记名称、适用主版本、接口/字段及行为、不可用时的 UI 和回退策略。能力清单见下表；不能据此认定历史版本已实现相应声明。
- 能力含义一旦发布不得原地变更为不兼容含义；确需改变时使用新名称，并在过渡期按实际实现声明旧、新能力。一般功能不单独引入版本范围或协商机制。
- 连接、切换节点、重连及检测到节点升级后刷新声明，按节点 ID 隔离缓存。发现请求失败是“未知”，不是空能力集合；格式损坏同样为未知。能力不绕过认证、审批或服务端执行前检查。

### 当前登记能力（API v1）

| 名称 | 契约范围 | 不支持时的行为 |
| --- | --- | --- |
| `voice.direct` | 节点 `/v1/speech/access` 签发授权后直连 VPS 语音；细节见 [共享 ASR](shared-asr.md) | 禁用麦克风，不回退到不同传输契约。 |
| `voice.stream` | 直连节点 `/v1/speech/streams` 的创建、PCM 分块、结束和取消 | 禁用麦克风；已有运行时语音能力检查仍生效。 |
| `session.goals` | `/v1/goals/capabilities`、会话目标读写及 `requireGoalSupport`；细节见 [目标模式](goal-mode.md) | 禁用目标模式，普通文本发送仍可用。 |
| `attachments` | 项目/会话/待办附件上传及消息 input 中的图片、文件等非文本引用 | 禁用聊天附件入口，阻止不支持的上传和附件消息；保留草稿供移除附件。 |
| `todos` | `/v1/todos` CRUD、详情及派发；细节见 [HTTP API](API.md) | 待办页显示不可用原因，不发送待办请求。 |

节点只声明 Relay 已实现的契约，不以原生后端当时是否可用决定是否声明。现有其他扩展保留既有探测和错误处理；新增可选行为必须先登记能力，不能擅自加入基础聊天的必需流程。

### 实现约束

- App 支持集合源于 `client/android/app/src/main/assets/api-compatibility.json`；构建据此生成客户端常量，发布器从 APK 的同一资产读取清单，VPS 打包再核对，拒绝缺失/非法或与本地发布不一致的声明。
- 普通业务客户端首次请求前读取声明；重连使缓存失效，后续业务请求最多复用 15 秒的声明。节点身份必须匹配配对记录。声明及发布版本变化刷新语音能力缓存。
- 更新检查按所有已有节点身份的绑定评估，包括授权已失效的绑定；只有地址、从未配对的记录不计为绑定。每个节点检查上限 12 秒，超时/离线/授权失效为未知，不使用业务缓存放行安装。
- 更新入口先检查兼容性，再下载；进入系统安装器前再检查。部分节点可用的确认仅针对该 APK 和整组检查结果，任一结果变化后重新确认。兼容性检查不强制切换节点。

## 历史版本迁移

已有 `/v1` 路径不自动证明历史版本符合本文的完整基础契约。缺少 `compatibility` 的旧节点先标记“兼容性未知”，不追溯授予 v1 合规声明。

本次没有为历史发布建立合规白名单，所有缺少声明的历史节点在更新判断中保持未知。今后若要认定历史版本兼容，须先做基础契约验证；只有可可靠识别且有验证记录的版本，才可通过小范围迁移适配认定支持 v1，并沿用已有的明确能力探测。无法识别、releaseCode 为 0 或没有验证依据时保持未知。这是历史迁移例外，不扩展成长期发布版本兼容矩阵。

兼容性未知不自动删除配对或禁止当前已工作的旧连接；保留既有连接流程和错误处理，但不能把它作为“候选新版 App 一定可用”的依据。

## App 更新判断

### 候选版本信息

App 更新清单包含 `compatibility.apiVersions`，声明该 APK 实际支持的基础 API 主版本集合，与 APK 内声明保持一致，并绑定同一发布产物。该字段沿用现有 HTTPS 信任及 APK 大小、SHA-256、签名验证流程，不替代这些检查。

缺少或非法的候选声明视为未知。发布成功、节点包与 APK 来自同一提交、两端软件版本号相同，都不能代替对绑定节点的判断；节点可能仍在运行旧包。

### 单个节点的结果

设候选 App 支持集合为 C，节点支持集合为 S：

| 条件 | 结果与行为 |
| --- | --- |
| 声明有效，且 C 与 S 有交集 | 基础兼容；使用最高共同版本。可选能力不足仅限制相关功能，不阻止 App 更新。 |
| 声明有效，但无共同版本 | 不兼容；提示节点需要升级，或保留当前 App。 |
| 节点离线、读取失败、未验证的旧节点、候选声明缺失等 | 未知；不能按兼容放行，也不能报告为已确认不兼容。 |

安装判断使用本次检查成功获取的、绑定到真实节点身份的声明。历史缓存仅用于展示，不凭离线缓存自动放行。进入系统安装前重新检查；检查后节点仍可能变化，因此 App 安装后连接时也必须执行兼容判断。

### 所有绑定节点的决策

- **只绑定一个节点**：确认基础兼容才进入安装流程。不兼容时显示“等待节点升级”；未知时显示具体原因并允许重新检查，保留当前 App。
- **绑定多个节点**：逐个展示结果。全部兼容可继续；至少一个兼容但其他不兼容/未知时，明确列出更新后可能不可用的节点，由用户确认后继续。没有任何已确认兼容节点时暂缓安装，不能因存在未知节点而放行。
- **尚未绑定节点**：不存在已有访问需要保留，可按常规更新；后续配对/连接时检查兼容性。
- 下载可以预先完成；安装门控与下载完整性检查分开。现有 Android 系统安装确认仍保留，不做静默安装，也不自动解绑、切换业务节点或强制节点升级。

本规则约束本版及后续 App 内置更新入口，无法让已安装的旧 App 自动获得拦截逻辑。外部手动安装无法由旧 App 拦截，因此新版连接时仍须给出兼容/不兼容/未知状态及可执行提示，保留配对数据；没有共同协议时不得发送业务写请求。

## 验收要求

实现按改动范围验证以下规则；实际执行范围见 [本次验证记录](validation-api-compatibility-20261112.md)：

- 旧客户端连接新服务端、新客户端连接旧服务端，均通过共同主版本完成基础文本聊天、回执核对、事件断线恢复和审批处理；验证无重复写入。
- 不认识的附加字段、通知和条目类型按安全规则处理；可选能力缺失只影响对应功能。
- 有共同版本、无共同版本、声明缺失/非法、历史迁移、节点离线分别产生正确结果；兼容与业务就绪状态分别展示。
- 单节点、多节点、无绑定节点及下载后安装前节点状态变化均符合更新规则；发布清单与 APK 支持集合一致。

契约测试验证声明是否真实；协议声明本身不是正确性的证明。当前既有发布不能仅因版本号高于某值就视为通过这些验收。
