# GitHub PR 提交规范

参考 MergeDemo 的 PR 作者流程、版本摘要与审核约定，适配 Rivo Relay 的单一 `main` 主线及 VPS 发布流程。本文件是 Git 与 PR 流程的唯一规范入口；验证与发布要求见根目录 [AGENTS.md](../AGENTS.md)。

## 意图与授权

| 用户请求 | 执行范围 |
| --- | --- |
| 开发、修复、建立规范 | 完成本地改动与适用验证，不自动 commit、push 或创建 PR |
| 创建需求分支 | 只准备分支，不自动实现需求或创建 PR |
| 提交 | 将本次明确范围提交到本地功能分支，不自动推送 |
| 推送 | 推送指定功能分支，不自动创建 PR |
| 提交 PR、创建 PR、更新 PR | 包含创建/复用功能分支、暂存本次文件、commit、push、创建/更新 Ready PR；已有 Draft 按请求转 Ready |
| 提交草稿 PR | 创建/更新 Draft，列明剩余事项 |
| 检查、审核 PR | 只读检查并在当前会话反馈；向 GitHub 提交 Review、解决 conversation、Approval、合并分别需要明确授权 |
| 发布、发布新版 | 按现有发布约定执行 VPS 发布，不自动推送、创建 PR、Git tag 或 GitHub Release |

创建或更新 PR 成功后交付链接，不自动监控、合并、切换或删除本地分支。工作未完成或存在相关验证失败时，先处理或说明阻塞，不创建 Ready，也不擅自改为 Draft。

## 分支与提交

1. 检查 `git status`、当前分支、远端和本次 diff，区分已有改动与本次改动。远端为 `origin`（`ethanhubin/rivo-relay`），目标分支为 `main`。
2. 新需求先 `git fetch origin main`，从最新 `origin/main` 以 `--no-track` 创建 `codex/<需求名>`。设置 `git config branch.<工作分支>.gh-merge-base main`，首次推送使用 `git push -u origin <工作分支>`。有效的已有功能分支可继续使用，不为提交机械同步主线；已合并或关闭的 PR 使用新分支承接新需求。
3. 有未提交改动时保留原改动；需要隔离时使用独立 worktree，只迁移本次内容，不自动 stash、丢弃或带入无关提交。无法安全区分时再澄清范围。
4. 只暂存本次明确的文件或补丁，不使用 `git add .`。提交前检查暂存 diff，不提交密钥、令牌、签名文件、APK、运行数据或临时验证产物。
5. 提交标题和 PR 标题使用 `<type>: <具体中文变化>`，类型按实际用途选择 `feat`、`fix`、`perf`、`refactor`、`docs`、`test`、`build` 或 `chore`，例如 `fix: 修复会话重连后消息重复显示`。本轮提交正文保留与 PR 一致的“版本摘要”。

## PR 正文

使用 [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md)。普通 PR 默认只保留“版本摘要”和“验证”，通常合计 3–6 个短句；仅有必要实现取舍时增加“改动”，有实际兼容性影响、部署步骤或残余风险时增加“注意”。更新时按最终 diff 重写过时内容，不追加过程流水账。

正文首节有且只有一个 `## 版本摘要`，通常写 1–3 条、最多 5 条单行列表，每条不超过 80 字，分类使用 `新增`、`修复`、`优化`、`调整`、`移除` 和中文冒号。例如：

```markdown
## 版本摘要

- 修复：恢复网络连接后，会话不再重复显示已接收消息。

## 验证

服务端相关回归测试通过；本轮未进行真机或模拟器验证。
```

摘要写对象和具体行为变化，不列文件名或测试结果，不手填版本号、PR 编号或提交数。性能结论有实测才写提升数值，并在验证中说明平台、场景和依据。纯文档、测试整理或无外部行为变化的内部重构可单独写 `- 无用户可见变化`，必要说明放“改动”。

验证说明实际完成的检查与结果、关键未验证项，以及真机/模拟器范围。未运行或中断不得写成通过；已有适用结果可以复用。默认一句概括，不粘贴命令或日志，需要追溯时链接已有证据。仅文档改动检查内容与 diff；提交本身不触发构建、发布、全量测试或 lint。

## 创建与更新

- 使用本地 Git 和 `gh`，创建前核对仓库、head、base，以及 `origin/main...HEAD` 的完整差异，确保只包含本次需求；检查同一 head 是否已有开放 PR，优先更新原 PR。
- 使用 `gh pr create --base main --head <工作分支> --title <标题> --body-file <正文文件>`；草稿加 `--draft`。更新使用 `gh pr edit <编号>` 的标题与 `--body-file` 参数。多行正文写入临时文件，保留真实换行。
- 处理审核反馈时更新原 PR，不擅自解决 Reviewer 尚未确认的 conversation，不自行 Approval 或合并。
- 用户明确要求“创建快速 PR”时，保留分支、范围、摘要及已知失败检查，复用已有验证，不额外启动测试；验证栏注明“本轮未执行（创建快速 PR）”，可补充此前实际完成的检查。快速流程不能绕过已知失败。

## 审核与合并

- 检查远端当前 head 的完整 diff、目标分支、摘要、验证结果、冲突及未解决讨论。代码更新后重新确认受影响结论，旧 head 的检查不能冒充当前结果。
- Review 只提交可执行问题；批准前确认问题已解决、验证充分。作者不能自批，可报告自查结果。缺少独立 Reviewer 时不强加 Approval 门槛，仍需完成最终检查并获得明确合并指令。
- 获得合并授权后，确认当前 head 无冲突、相关检查通过、阻塞问题和讨论已解决，遵守仓库实际保护规则，不绕过 required checks。普通功能 PR 默认 Squash merge，以当前 PR 标题和正文显式设置合并提交消息，保留唯一“版本摘要”章节；标题附真实 PR 编号。
- 使用 `gh pr merge <编号> --squash --subject '<PR 标题> (#<编号>)' --body-file <正文文件>`。合并后可删除已合并的远端功能分支；保留 `main`，本地分支与 worktree 清理另按用户要求执行。
- 合并不自动递增 Android 版本、部署或发布。版本摘要保留在 Git 中供追溯；本规范不表示现有发布 CLI 已实现摘要自动提取。

## 仓库设置

本规范不自动修改 GitHub 设置。小团队默认不新增 CODEOWNERS、多级审批、强制 Draft、标签或 PR 大小门槛；具备条件时再配置分支保护、禁止强推/删除和 discussion resolution，有可靠 CI 后再设置 required checks。仓库设置变更需单独授权。
